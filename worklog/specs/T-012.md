### Objective

Prepare the integration architecture, evidence map, acceptance gates,
manuscript plan and reproducibility checklist **before** all scientific
dependencies have completed.

This stage must **not** perform final scientific integration. The repository's
dependency graph remains authoritative, and final T-012 stays blocked by T-010
and T-011.

### Prerequisites

Accepted `main` only. The pre-integration branch is cut from `main`, not from
any task branch, and contains only work derived from accepted `main` plus
explicit readiness metadata about pending tasks.

### Allowed paths

    paper/INTEGRATION_PLAN.md
    results/tables/t012-integration-readiness.md
    reviews/T-012/HANDOVER.md
    worklog/specs/T-012.md
    worklog/M1.md

### Forbidden

- Performing final scientific integration, or marking T-012 `done` / `review`.
- Weakening or removing `T-010 + T-011 -> T-012` from the dependency graph, or
  inventing a new dependency to justify preparatory work.
- Merging, cherry-picking, copying or rewriting another member's work; editing
  their branches, worklogs or review packages.
- Continuing T-008 modelling, or modifying T-008 code or pull-request content.
- Editing scientific implementation code under `src/quality/`, `src/mixture/`,
  `src/scaling/`, `src/panel/`, `src/alloc/`, `src/evolution/`.
- Writing final manuscript conclusions whose evidence is not yet reviewed and
  accepted, including a final abstract.
- Adopting a numerical or scientific claim from an unreviewed branch as
  accepted project evidence.

Branch metadata and pull-request metadata **may** be inspected to establish that
pending work exists. Anything obtained that way is marked
`UNREVIEWED / NON-AUTHORITATIVE / NOT FOR MANUSCRIPT CLAIMS` and its scientific
conclusions are not copied into the plan as facts.

### Acceptance criteria

The stage fails if any of the following is not true.

1. The branch is cut from accepted `main` and contains no content merged,
   cherry-picked or copied from a task branch.
2. A cross-question interface matrix exists covering IF1-IF4 with, per row:
   producer, interface, consumer, schema/semantic contract, unit/scale,
   provenance class, validity region, required uncertainty, acceptance gate,
   current readiness, and prohibited downstream interpretation.
3. An evidence-to-claim map exists covering Q1-Q4 and the cross-cutting
   classes, each claim carrying its minimum supporting artifact, mandatory
   caveat and one of `READY` / `PENDING REVIEW` / `BLOCKED` / `NOT STARTED`.
   Where evidence does not exist the entry reads
   `BLOCKED - DO NOT WRITE AS A RESULT`, never a placeholder number.
4. A five-level claim hierarchy (A direct, B model-conditional, C
   semi-synthetic calibration, D extrapolation, E unresolved/diagnostic) is
   defined, and every future quantitative claim is required to be classifiable
   into it. The hierarchy is not used to score people or tasks.
5. A figure and table inventory records, per item: ID, question, purpose,
   producer, source artifact, dependency, provenance class, whether uncertainty
   must be shown, manuscript destination and readiness. No speculative final
   figure is generated and no plot type is locked before its producing task is
   accepted.
6. A units, scales and direction audit exists for N, D, Loss, Q, p, benchmark
   scores, compute, time, context length, uncertainty types and the validity
   box, each with canonical representation, source contract, known conversion,
   downstream risk and acceptance check. An ambiguous convention is recorded as
   ambiguous rather than silently resolved.
7. Every manuscript section is classified as `STRUCTURAL PLACEHOLDER`,
   `SAFE GENERIC PROSE`, `ACCEPTED SCIENTIFIC CONTENT` or
   `PREMATURE / MUST NOT FINALIZE YET`, with an evidence owner and the trigger
   that makes it eligible for final writing.
8. Final acceptance gates G1-G12 are specified with owner, evidence, pass
   condition and current state.
9. The review package states explicitly that pre-integration readiness work
   exists but final T-012 remains dependency-blocked, and that no unreviewed
   scientific result was adopted.
10. Interface self-test, whitespace check and the public-safety gate pass; no
    absolute machine path, ignored dataset, or another member's path enters the
    commit.

```text
Run from the intended `modeling-research-2026` repository root.

FORMAL T-012 v1 PRE-INTEGRATION STAGE

Purpose: prepare the integration architecture, evidence map, acceptance gates,
manuscript plan and reproducibility checklist BEFORE all scientific
dependencies have completed. This stage MUST NOT perform final scientific
integration.

The dependency graph remains authoritative:

    T-007 -> T-008
    T-008 -> T-010
    T-008 + T-009 -> T-011
    T-010 + T-011 -> T-012

Therefore T-012 final integration remains blocked by T-010 and T-011; this
stage is PREPARATORY ONLY; it must not convert unreviewed branch outputs into
accepted scientific facts; it must not merge, cherry-pick, copy or rewrite
another member's work; it must not continue T-008 modelling; and it must not
write final manuscript conclusions whose evidence is not yet reviewed and
accepted.

0. START FROM CLEAN MAIN, NOT FROM THE T-008 BRANCH

Verify the repository root, remote, status, current branch, and the log across
all refs. The T-008 draft pull request is a REVIEWED/FROZEN checkpoint: do not
continue working on its branch and do not merge it. Require the T-008 working
tree to be clean before leaving it.

Check out `main`, fast-forward, and require local `main` to equal `origin/main`
with a clean tracked working tree. Create `chore/m1-T012-preintegration` and
push it early. Do not branch from the T-008 pull request. Do not merge or
cherry-pick the Q1, Q4 or T-008 task branches. This branch must contain only
work derived from accepted `main` plus explicit readiness metadata about
pending tasks.

1. READ THE GOVERNANCE AND CURRENT CONTRACTS

Read the repository README, the agent contract, the coordinator instructions,
the task register, the shared interface module, the review-package and
prompt-spec conventions and templates, the coordinator worklog, the manuscript
entry point, the 2026 format conformance record, the bibliography and every
manuscript section. Inspect only the ACCEPTED main-branch artifacts relevant to
Q1-Q4.

Branch and pull-request metadata may be inspected to know that pending work
exists. Numerical or scientific claims from an unreviewed branch may NOT be
adopted as accepted project evidence. Anything read from a pending branch
solely to understand interface or readiness state is marked
UNREVIEWED / NON-AUTHORITATIVE / NOT FOR MANUSCRIPT CLAIMS, and its scientific
conclusions are not copied into the integration plan as facts.

2. ARCHIVE THIS PROMPT

Create the T-012 prompt specification using the existing convention, recording
the substantive instructions. It must be machine-independent: no drive letters,
no local usernames, no private machine information, no provider account,
endpoint or quota information. Its execution premise is to run from the
intended repository root. Do not modify earlier prompt specifications.

3. DO NOT MISREPRESENT T-012 STATUS

Final scientific integration has not started in the dependency-graph sense
because T-010 and T-011 are incomplete. Do not mark T-012 `done` or `review`;
prefer leaving it `todo`. Do not weaken or remove `T-010 + T-011 -> T-012`. The
review package must state that pre-integration readiness work exists but final
T-012 remains dependency-blocked. Do not invent a new scientific dependency to
justify this preparatory work.

4. BUILD A CROSS-QUESTION INTERFACE MATRIX

Create the integration plan as a technical document, not manuscript prose, with
a matrix covering at least: producer task, interface/artifact, consumer task,
schema/semantic contract, unit/scale, provenance class, validity region,
uncertainty required, acceptance gate, current readiness, and prohibited
downstream interpretation.

Cover IF1 domain quality (producer Q1; consumers Q2 and Q3 where applicable),
preserving: quality in the unit interval; accepted indicator directions
standardized higher-is-better; quality domains are not identical to the
seventeen mixture domains; mapping may be partial; coverage fraction is
empirical mapped mixture mass, not a ratio of domain counts; domain interval
and sample size travel with the score; unmapped domains must not receive
invented quality scores. Status PENDING REVIEW until independently reviewed.

Cover IF2 mixture response (producer Q1; consumers Q2 and Q3), preserving:
seventeen-domain simplex semantics; declared contrast basis; zero policy;
renormalisation; validation split; domains without loss; provenance; and that
no coefficient may be interpreted without its reference basis. Status PENDING
REVIEW.

Cover IF3 scaling law (producer Q2; consumers Q3 and Q4 where justified),
distinguishing the classic object available locally with quality pinned to one
from a generalized object NOT YET EMITTED. Preserve: the organizer label and
the numerical fingerprint of the principal training-log table are separate
facts; the classic fit supports estimator/generator recovery on that table;
empirical external support comes from independent validation such as the
cross-family table excluding overlapping same-family rows, and the literature
table; the quality-bearing tables are not ordinary observed quality
experiments; the quarantined table's quality semantics remain unresolved; no
final empirical quality exponent exists; and candidate analytical identities
are not equivalent to an adopted empirical generalized law. Generalized status
BLOCKED ON REVIEWED IF1/IF2 AND T-008 CLOSURE.

Cover IF4 loss/benchmark bridge (producer Q4 forecasting task; consumer the
manuscript integration), requiring explicit comparability strata, primary
stratum, prediction error, anchor count, benchmark score scale and provenance.
Status NOT YET PRODUCED. Do not infer it from preliminary panel work.

5. BUILD THE EVIDENCE-TO-CLAIM MAP

Add a second matrix mapping future manuscript claims to required evidence, to
prevent a polished manuscript from silently turning diagnostics into
conclusions, semi-synthetic fits into empirical facts, extrapolation into
validation, and unreviewed branches into accepted evidence.

For every claim class give: claim, minimum supporting task/artifact, mandatory
caveat, and current state among READY, PENDING REVIEW, BLOCKED, NOT STARTED.

Cover at least - Q1: definition of overall and domain quality; reliability and
uncertainty; indicator conflict findings; replication of the secondary
attachments; domain mapping and mapped-mass coverage; mixture effects and
interactions; extrapolation across scale. Q2: classic scaling; principal-table
fingerprint interpretation; observed external validation; quality dependence;
quality/parameter substitution; large-model extrapolation. Q3: compute-feasible
optimization; fixed-quality analytical benchmark; optimized quality; quality
budget share; critical context length; structural transitions; comparison of
quality-cost functions. Q4: panel population; model-type strata; detailed-task
reconciliation; loss/benchmark bridge; scale versus non-scale decomposition;
historical technical progress; twelve-month frontier; twenty-four-month stress
forecast. Cross-cutting: uncertainty; external validity; extrapolation;
provenance; negative results.

Where evidence does not yet exist write `BLOCKED - DO NOT WRITE AS A RESULT`
rather than a placeholder numerical conclusion.

6. DEFINE THE MANUSCRIPT CLAIM HIERARCHY

Define levels A direct supported result (accepted task output plus reproducible
tracked evidence); B model-conditional result (exact consequence conditional on
an explicitly stated model form); C semi-synthetic calibration (numerical
behaviour supported primarily by organizer-labelled semi-synthetic or generated
data); D extrapolation (evaluation outside the identifying support or validity
region); E unresolved or diagnostic only. Require every future quantitative
claim to be classifiable into one level. Do not use the hierarchy to score team
members or tasks.

7. PREPARE A FIGURE AND TABLE INVENTORY - DO NOT CREATE FINAL FIGURES YET

Specify the minimal final figure and table set. Do not generate speculative
final figures. Record per item: ID, question, scientific purpose, producer
task, source artifact or script, dependency, provenance class, whether
uncertainty must be shown, manuscript destination and current readiness. Prefer
a compact final paper. Do not lock exact plot types before the producing task
is accepted.

8. AUDIT UNITS, SCALES AND DIRECTION CONVENTIONS

Create a readiness audit table - not a scientific-results table - covering the
cross-question conventions currently encoded in accepted main: parameter count;
token count; loss; quality; mixture vector; benchmark scores; compute; time;
context length; confidence and uncertainty types; and the validity box. For
each state canonical representation, source contract, known conversion,
downstream risk and acceptance check. Do not silently choose a unit where the
contract is ambiguous.

9. AUDIT THE CURRENT MANUSCRIPT SKELETON

Inspect every manuscript section. Do not write the final scientific paper. For
each section classify the current state as STRUCTURAL PLACEHOLDER, SAFE GENERIC
PROSE, ACCEPTED SCIENTIFIC CONTENT, or PREMATURE / MUST NOT FINALIZE YET, and
define the intended evidence owner. State when each section becomes eligible
for final writing. In particular do not finalize the abstract before all four
questions have accepted results; do not write Q1 numerical conclusions before
the Q1 task is reviewed; do not write generalized Q2 numerical conclusions
before the Q2 task closes; do not write Q3 conclusions before the Q3 task; do
not write Q4 decomposition or forecast conclusions before the Q4 forecasting
task; and require the validation and evaluation sections to distinguish
interpolation, observed validation, semi-synthetic calibration and
extrapolation.

10. DEFINE FINAL ACCEPTANCE GATES

Write an explicit final-integration gate checklist. Final T-012 must not begin
or close until all applicable gates pass. At minimum: G1 Q1 accepted with
reviewed IF1 and IF2; G2 Q2 closed with a final decision on the generalized law
and a final IF3 or an explicit justified alternative; G3 Q3 accepted with
optimizer and sensitivity evidence; G4 panel task accepted with its foundation
and reconciliation limits; G5 forecasting task accepted with decomposition,
IF4, forecast and uncertainty; G6 all emitted interface objects validate and
schema versions are compatible; G7 all manuscript numbers regenerate from
tracked scripts; G8 no semi-synthetic or generated result is presented as
observed evidence; G9 every headline estimate uses the uncertainty type its
data justifies; G10 the manuscript format rules still pass after scientific
content is inserted; G11 no raw, private or local-only source enters version
control; G12 a final rendered-document visual audit covering pagination,
figures, tables, glyphs, references and identity rules. For each gate specify
owner, evidence, pass condition and current state.

11. DEFINE HANDOFF AND REVIEW ORDER

Record the intended integration order: Q1 review, then Q2 closure, then Q3; and
in parallel the panel-task review, then the forecasting task; then Q3 plus the
forecasting task into final integration. Do not require the panel task merely
to unblock Q2. Do not require the third member to finish before the coordinator
can close Q2 once reviewed IF1/IF2 exist. Do not begin Q3 scientific
conclusions before the final IF3 exists. Do not allow the forecasting task to
treat provisional Q2 or unreviewed panel artifacts as accepted inputs.

12. PREPARE THE REVIEW PACKAGE

Create the T-012 review package describing PRE-INTEGRATION ONLY, stating the
status as pre-integration readiness complete with final T-012 still
dependency-blocked. Include branch and base; what was inspected; the
integration matrix; the evidence-to-claim map; the unit and scale audit; the
manuscript readiness audit; the final acceptance gates; unresolved
dependencies; an explicit statement that no unreviewed scientific result from
another member was adopted; and the exact next trigger for resuming final
integration. Do not imply final scientific integration is complete.

13. WORKLOG

Append one accurate pre-integration entry to the coordinator worklog recording:
planning only; artifacts created; active effort rounded to half an hour; the
assistant used; validation performed; dependencies intentionally not consumed;
and status as a preparatory checkpoint with final integration blocked. Do not
rewrite older entries.

14. VALIDATION

Run the interface self-test, the whitespace check and the public-safety gate in
pre-commit mode. Verify manually: no absolute machine path in tracked files; no
ignored or local dataset staged; no path owned by another member modified; no
T-008 code or pull-request content modified; no scientific value copied from an
unreviewed branch; T-012 not marked complete; the dependency graph intact;
every planned manuscript claim carrying an evidence owner and gate; every
cross-question quantity carrying explicit units, direction and provenance; and
the abstract still unwritten as a scientific summary.

Allowed tracked paths for this stage are the integration plan, the readiness
audit table, the T-012 review package, the T-012 prompt specification and the
coordinator worklog. Do not edit scientific implementation code, another
member's worklog or review package, or another member's branches. Use focused
commits of the form `docs(integration): ... [T-012]`, ASCII, one line, at most
72 characters, preferring a small number of conceptually coherent commits. Push
the branch and open a DRAFT pull request into the main branch as a preparatory
architecture and readiness checkpoint. Do not merge it. Do not mark T-012 done.

16. STOP CONDITIONS

Stop rather than improvise if a required interface semantic is ambiguous in the
shared interface module; if accepted main contains contradictory units or
conventions that cannot be reconciled without a scientific decision; if
preparing the plan would require modifying a path owned by another member; if a
pending branch contains a tempting result that has not been reviewed; if the
dependency graph would need changing; if a new shared interface field appears
necessary; or if the public-safety gate fails. Record the issue in the handover
rather than silently solving a scientific problem inside an
integration-planning task.
```
